Decision Diamond 2.0 - Object expansions

Today the Decision Diamond evaluates only Contact, forcing customers to stitch automations and tag workarounds together to handle work that lives on deals, invoices, and appointments. This project expands it to evaluate those objects alongside Contact, so customers can configure flows like estimate follow-ups, post-job reviews, no-show handling, and deal-value routing in a single node.

Phase I is our first batch to validate this concept, shipping four priority trigger sequences: Product is purchased, Appointments, Pipeline stage is moved, and Quote status. Remaining sequences will follow as prioritized.

A new in-context AI assistant inside the Decision Diamond helps customers translate intent into rules. We’re starting here because it’s where customers spend the most effort, setting up our broader move toward an AI-oriented product.

In parallel, a UX audit of the current Decision Diamond surfaces 8 findings, including critical bugs that affect the success of 2.0. Some fixes apply to the automation builder broadly; others to Decision Diamond specifically. PM leads prioritization, and several improvements will ship ahead of the core work.

Problem

What’s blocking customers today

Decision Diamond is constrained on two fronts. The engine doesn’t see the objects customers actually work with, and the current configuration has discoverability issues and usability gaps. Together they erode customer trust and cap what we can deliver.

01 / Engine

Object blindness

Local service businesses operate on deals, jobs, appointments, and invoices, but the automation engine is contact-centric. Triggers, conditions, and actions all assume Contact is the primary object. The vertical use cases template builders need to ship (estimate follow-ups, post-job review requests, no-show handling, deal-value routing) aren’t possible today without workarounds: multiple automations, complex tag chains, and manual intervention.

02 / Configuration UX

Discoverability and usability gaps

The current Decision Diamond has layered issues uncovered in the UX audit. Discoverability gaps make key actions and states hard to find. Usability problems force valid configurations into clunkier paths than necessary. Together, the audit findings block users from configuring, validating, and publishing branching logic with confidence.

Product scope

What we’re building and who it’s for

Decision Diamond evaluates one object today: Contact. This project expands it to evaluate deals, invoices, appointments, and companies, the objects local service businesses actually run their work on. A second workstream addresses the UX audit of the current Decision Diamond so the expanded experience is usable end-to-end.

Audience

Three audiences in priority order: the ICP we’re serving, the people who build templates on their behalf, and the operators inside those accounts who edit and validate what gets shipped to them.

Primary ICP · validated
Local service businesses
12 verticals confirmed by Tyler Garns and product marketing on April 13, 2026. Field service and trades dominate (HVAC, plumbing, roofing, cleaning, pest control). Healthcare is the outlier with HIPAA and different tech maturity. These users think in deals, jobs, appointments, and invoices, not in tags applied to contacts.
Direct configurators
Template builders
Tyler’s team, onboarding coaches, and partners. They build the campaigns that get launched on a customer’s first onboarding call, so they configure Decision Diamonds repeatedly and feel every UX gap directly.
Downstream
End operators inside ICP accounts
CRM admins, marketing operators, and small-business owners who view, edit, and validate templated automations in their account. They rely on Test, Save, and clear branch labeling to trust what they’re publishing, which are exactly the gaps the audit surfaces.

Spec

Complete trigger entity attribute reference

Detailed attribute reference for each priority trigger sequence. Source of truth for grooming with PM and engineering.

1

Product is purchased

“When a purchase is made”

Attribute Required Type Options / behavior Dependency
Select purchase type Yes Single-select Product (specific product) or Any purchase (any product). Top-level driver
Select products Conditional Multi-select with categories Full product catalog. Each item shows its category. Only appears when purchase type = Product. Hidden when Any purchase.
Payment type Optional Multi-select Credit Card (charge now), Credit Card (manual), Check, Cash, Money Order, Adjustment, Include $0 invoices, Any payment type. Always visible
2

Quote status

“Trigger when a quote changes status”

Attribute Required Type Options / behavior Dependency
Trigger when quote is… Yes Single-select Sent, Viewed, Accepted (payment options unavailable). None. Only attribute on this trigger.
3

Pipeline stage is moved

“Pipeline stage move”

Attribute Required Type Options / behavior Dependency
When moving Yes Single-select Into (deal moves into selected stage) or Out of (deal moves out of selected stage). Top-level direction selector
Pipeline Yes Single-select List of all configured pipelines in the account. Independent, but its value drives the Stage options.
Stage Yes Single-select List of all stages belonging to the selected pipeline. Dependent on Pipeline. Stages shown change with pipeline selection.
4

Appointment

“When a contact schedules, reschedules, or cancels”

Attribute Required Type Options / behavior Dependency
When a contact Yes Single-select Schedules, Reschedules, Cancels. Top-level event selector
Select an appointment type Yes Single-select List of all appointment types configured in the account, each shown with duration. Always shown. Same field under all three When-a-contact options.

Conditional logic summary

  • Product is purchased: the “Select products” picker only appears when “Select purchase type” = Product. Choosing “Any purchase” removes it while Payment type stays visible.
  • Pipeline stage is moved: the “Stage” dropdown is populated dynamically based on the selected “Pipeline”. Changing pipeline replaces the stage list.
  • Quote status and Appointment: no conditional show/hide. All fields visible regardless of upper drop-down values.

UX audit workstream · current Decision Diamond

Trust-layer fixes — eight findings on the existing DD

A parallel workstream to entity expansion: a UX audit of the current Decision Diamond. These findings exist independent of the new entities being added — they’re structural gaps in today’s configuration UX that will surface louder once DD is evaluating five entities instead of one. Fixing them in parallel keeps the expanded engine trustworthy at launch.

AUD-05 Medium

Title doesn’t scale across entity types

Enhancement· Decision Diamond
▢
Image 5 — hardcoded title highlighted in red
images/aud-05-title-scaling.png
Pain point

The current heading hardcodes “What rules must a contact meet to be allowed into the ‘Sequence’ sequence?” As the product introduces additional entities beyond Contact and Sequence, this copy won’t carry over and will require manual updates for each new entity.

Recommendation

Shorten the heading to “Rules for ‘[Entity Name]’” with the entity name dynamically bound, and remove the descriptive sub-question. Pattern then scales across current and future entity types.

AUD-06 Medium

Decision diamond not fully responsive

Bug· Decision Diamond
▢
Image 1 — panel overflows backdrop at smaller width
images/aud-06-responsive.png
Pain point

The current structure is retained, but layout breaks exist within that structure at smaller breakpoints, causing fields and panels to overflow or misalign.

Recommendation

Full responsive audit in progress. Findings will be documented per breakpoint with annotated specs before engineering handoff. Target breakpoints: 1440 / 1024 / 768.

AUD-02 High

No Save action on the config screen

Bug· Decision Diamond
▢
Needed: capture of panel header (and Save mock)
images/aud-02-no-save.png
Pain point

The configuration screen is missing a Save button. Users have no clear way to commit their changes or confirm that work has been persisted, breaking a foundational expectation of any configuration flow.

Recommendation

Add a primary Save action with explicit enabled / disabled / saved states. Confirm with engineering whether auto-save exists; if so, surface persistence status so users have visible feedback.

AUD-01 Critical

Test function returns incorrect results

Bug· Decision Diamond
▢
Image 2 — Test panel modal with red errors
images/aud-01-test-wrong.png
Pain point

The Test action runs but produces the wrong outcome even when input matches the configured rule criteria. Users rely on Test to validate logic before publishing — an unreliable Test is worse than no Test, because users will publish based on misleading feedback.

Recommendation

Engineering investigation into the evaluation logic is required. In the interim, surface a known-issue state on the Test panel so users do not act on incorrect output.

AUD-08 Low

Default rule set count adds unnecessary input

Enhancement· Decision Diamond
▢
Pair: Image 2 (same source as AUD-05 — two rule sets visible)
images/aud-08-default-rulesets.png
Pain point

The screen always renders two rule sets by default, even when only Rule 1 is needed. The empty second set creates visual noise and implies a required input that isn’t actually required.

Recommendation

Default to one rule set, with an “Add rule set” affordance for users who need more. Aligns with progressive disclosure.

AUD-03 High

Duplicate panel titles obscure which branch is being edited

Issue· Decision Diamond
▢
Pair: Image 5 (two panels titled "Rules for: Sequence")
images/aud-03-duplicate-titles.png
Pain point

When two downstream branches target sequences that share the same name, both panels render with the identical title “Rules for: Sequence.” No path indicator and no numbering — users cannot tell which rule set controls which target. Error cost is high; users can edit the wrong branch without noticing.

Recommendation

At minimum, auto-append a disambiguator at the panel level (e.g., “Sequence 1” / “Sequence 2”). Stronger: auto-rename every sequence to match the name of its function so identity is clear at the source.

AUD-04 High

Diamond doesn’t visually communicate branching on canvas

Issue· Overall impact
▢
Needed: canvas capture (Decision Diamond + two branch arrows)
images/aud-04-canvas-branching.png
Pain point

The diamond shape has one input and two outputs, but on the canvas it renders as a small icon with arrows identical to linear flow arrows. No Yes/No, True/False, or match labeling — users can’t tell which path is which without opening the node.

Recommendation

Add explicit branch labels on the canvas (e.g., “Matches” / “Doesn’t match”) and visually differentiate branching arrows from linear flow arrows. Applies to any future branching step in the automation builder.

AUD-07 Medium

Ambiguous status indicator (orange dot)

Issue· Overall impact
▢
Needed: canvas capture (orange dot + Ready to publish tooltip)
images/aud-07-orange-dot.png
Pain point

The orange dot and “Ready to publish” tooltip are not visually differentiated from warning / error states elsewhere on the canvas. Orange/yellow conventionally signals “attention needed” — using it to mean “ready” creates color-semantic conflict and trains users to ignore real warning states.

Recommendation

Reserve orange/yellow for warning states. Use a distinct color (e.g., green) for positive ready states. Audit color usage across the automation builder for system-wide consistency.

Counter-metrics (so we don’t game the numbers)

  • Drop-off at “Add rule set” — if AUD-08’s progressive disclosure hides functionality users need, we’ll see them stuck at a single rule set when their intent requires more.
  • Increase in published-but-broken automations — if Save and Test fixes give false confidence, ticket volume on logic errors could rise even as publish rate climbs.
  • Adoption of branching automations as a share of all automations — should hold or grow; a drop would suggest the rework made the feature feel more complex, not less.
Testing plan

Validating both workstreams

Qualitative validation before engineering scoping, quantitative pre/post tracking, and an A/B test for new ICP accounts. Phase 1 tasks now cover both entity expansion (configuring a Decision Diamond against a non-contact entity for a vertical scenario) and trust-layer audit fixes (Save, Test, branch identity). Per-finding validation criteria for the audit findings sit below the phases.

01

Pre-launch moderated usability test

Qualitative · 6–8 participants · 45 min

Participants split between new users (no Decision Diamond experience) and existing users (have published ≥3 automations). Designed to surface blockers before engineering scopes the redesign.

Tasks:

  • Configure a Decision Diamond that routes contacts whose First Name equals “Jake” into Sequence A, others into Sequence B
  • Save the configuration and confirm persistence (kill the tab, reopen, verify)
  • Run Test with a sample contact and predict the outcome before clicking Evaluate
  • Publish the automation
  • Return to the published automation and modify only the Sequence A branch — save again
Success criteria: 80%+ complete all tasks without facilitator intervention. Zero wrong-branch edits in task 5. Test outcome predictions match Evaluate output in 100% of attempts.
02

Quantitative pre/post tracking

Quantitative · all users · 12 weeks

Instrument all primary KPIs 4 weeks before release for baseline. Compare 8 weeks post-release. Segment by user tenure (new / established) and automation complexity (number of branches).

What we’re watching:

  • Publish completion rate — primary signal that Save and Test fixes unblocked the funnel
  • Wrong-branch edits — measured via undo within 60s of save; proxy for AUD-03 confusion
  • Time-to-publish for Decision Diamond configs — should decrease with title clarity (AUD-05), responsive fixes (AUD-06), and reduced default inputs (AUD-08)
  • Support ticket volume on automation topics — leading indicator of trust restoration
Success criteria: All four primary KPIs hit targets within 8 weeks. No counter-metric regression beyond pre-release noise floor.
03

A/B test for new users

Quantitative · new users only · 4 weeks

Random 50/50 split — control sees the existing Decision Diamond, variant sees the redesigned version. Restricted to new users so neither group has prior exposure to the legacy UI.

Hypothesis: the redesign produces a statistically significant lift in publish completion rate without a corresponding drop in branching automation adoption.

Success criteria: ≥10% absolute lift in publish completion at p < 0.05. Adoption of branching automations holds or grows.
